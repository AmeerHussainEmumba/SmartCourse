# Testing guide

Every test category SmartCourse uses, what it checks, why that check matters, and how to run it. This is the index RFC §18.8 requires: a future contributor deciding whether a change is safe should be able to answer "what would break" from this document, not by reading every test file.

## Quick reference

| Command | Runs | Needs Docker? |
|---|---|---|
| `make test` | Unit tests | No |
| `make test-race` | Unit tests, race detector on | No |
| `make test-integration` | Integration + concurrency + HTTP-level + workflow tests | Yes |
| `go test -tags=integration -race ./...` | Everything, one process | Yes |

CI (`.github/workflows/ci.yml`) runs the full set — build, `go vet`, `golangci-lint` (module-boundary `depguard` rules), migrations against a real Postgres service container, then `go test -race -tags=integration ./...` with `POSTGRES_DSN`/`REDIS_ADDR` set. The `-tags=integration` flag was missing until ADR-0025 (M2): every `//go:build integration` file — including the enrollment seat-limit concurrency test, the one RFC §18.3 calls "the highest-value tier" — was silently excluded from CI since the suite existed, found while verifying M2's own new integration tests actually ran. The job's declared Postgres/Redis service containers and its own migration step are themselves redundant now: every integration test provisions its own disposable containers via `testenv.Setup`, and nothing reads `POSTGRES_DSN`/`REDIS_ADDR` directly — left in place as a separate, lower-priority cleanup rather than touched here.

## Test tiers

### Unit — no database, no network

Domain logic tested against pure functions and in-memory state. Fast, run constantly during development.

| Package | What it checks |
|---|---|
| `internal/platform/auth` | argon2id hash/verify round-trips and rejects wrong passwords; the dummy hash (timing-safety, RFC §11.3) is itself valid; JWT issue/parse round-trips; expired tokens rejected; wrong signing key rejected; **`alg:none` / alg-confusion rejected** (`TestParseAccessToken_RejectsAlgNone` — this is the specific check that closes a real vulnerability class, not a generic parser test); `middleware_test.go` (new): `RequireAuth` rejects a missing/malformed header and an invalid token, and on success populates the request context with the caller's identity; `RequireRole` rejects when no identity is present and when the role isn't in the allowed set — both via a real `httptest`+`gin.Engine`, this repo's first use of that pattern, not a bare function call |
| `internal/platform/config` | `Load()`'s fail-fast validation: every required env var missing individually and in combination (confirming errors *aggregate*, not just that the first one reported); `JWT_SIGNING_KEY`'s minimum-length check; a malformed optional var (bad int/bool/duration) is rejected rather than silently falling back to its default |
| `internal/platform/httpx` | `EncodeCursor`/`DecodeCursor` round-trip exactly (including sub-second time precision); a malformed cursor (bad base64, or valid base64 that isn't valid JSON) is rejected as a client error, not a panic; `ClampLimit`'s boundary behavior (zero/negative, over-max, in-range) |

Run: `go test ./internal/platform/auth/... ./internal/platform/config/... ./internal/platform/httpx/...` or `make test`.

### Integration — real Postgres (and Redis, where relevant), via `testcontainers-go`

RFC §18.2's rule: **mocks are not used for the database.** A mock proves the code called the method it was written to call; it cannot prove a constraint holds, a transaction rolls back correctly, or a partial index behaves as designed. Every test in this tier spins up a real, disposable Postgres (and Redis) container via `test/integration/testenv`, runs all four services' migrations against it in order (`migrations/{platform,identity,course,analytics}/` — schema-per-service, ADR-0024), and tears it down after — no shared state between tests, no fixtures to go stale.

Build tag: `integration`. Excluded from `go test ./...` by default so unit tests stay fast; included by `make test-integration`.

| Package | What it checks | Why it matters |
|---|---|---|
| `internal/identity` | Duplicate email rejected (unique constraint); **case-insensitive** duplicate rejected (the `CITEXT` column, not an application `lower()` check that would race); login failure paths return identical error codes for unknown-email vs wrong-password; refresh rotation issues a new token and invalidates the old one; **reuse detection burns the whole token family**, not just the presented token; role change bumps `token_version` in Postgres **and** writes it to Redis in the same operation; **password reset revokes every refresh token**, not just future access tokens; **10 concurrent `/auth/refresh` calls with the same token yield exactly 1 success**; registration succeeds even when the verification email fails to send; `Logout` revokes its refresh token (and is a no-op on an unknown one); `GetMe`/`UpdateMe` reflect and persist real state, with `UpdateMe` writing `identity.user_profile_updated`; email verification's resend-then-confirm flow, including no email-enumeration on resend and a no-op on an already-verified account | Proves ADR-0015's rotation/reuse-detection design actually works, not just that it's documented; the last three are regression tests for real bugs caught in external review — see `internal/identity/README.md`'s "Bugs found during review"; the methods after that were previously untested at all |
| `internal/course` | Full create → author → publish → catalogue → detail → full-text search lifecycle (catalogue's instructor name now asserted via `instructor_mirror`, not a live join into `identity.users` — ADR-0024); `ValidateMetadata` rejects a draft with no modules; a non-owning instructor can't edit another's draft; an invalid slug format is rejected; `instructor_mirror` ignores an out-of-order `identity.user_profile_updated`/`user_registered` delivery; `DeleteModule`/`DeleteLesson`, `GetPublishStatus`'s non-owner/not-found branches, and `GetPublishedDetail`'s cache-miss-falls-back-to-Postgres path; `Service.Publish` itself (workflow ID construction, `SetVersionPublishing`, error mapping) via a fake Temporal client; `ListCatalogue` with a real, non-empty cursor (every other test only ever reads page 1); `handleUserRegistered`/`handleUserProfileUpdated` through a real outbox event and a real relay, not a direct repository call. The core lifecycle tests drive the publish activities directly (`ValidateMetadata` through `PromoteAndPublish`, same order `PublishCourseWorkflow` calls them in) rather than calling `Service.Publish` (which starts a real Temporal workflow and needs a live server) — see `internal/workflows` below for where the workflow itself is tested, and this row's `Service.Publish` entry for where the HTTP-facing method is tested in isolation | Proves blue-green promotion (ADR-0010) and ownership checks (RFC §11.4) hold against a real foreign-key-constrained schema — course creation's 3-step transaction order was itself a bug caught by this suite, not by reading the code; the catalogue's cross-schema join (now a mirror) and its ordering guard are both regression tests for bugs found live, not by inspection; `Service.Publish` and the relay-handler tests close gaps an audit found: the method that actually calls `ExecuteWorkflow`, and the payload-decoding path of a real event handler, both had zero coverage before |
| `internal/enrollment` | **Seat limit never exceeded under real concurrency** (30 goroutines, 10 seats — see below); duplicate concurrent enrollment attempts resolve to exactly one success; withdrawal then re-enrollment is permitted (partial unique index); enrolling in an unpublished course is rejected; `GetByID` returns an enrollment to its owner and rejects a different student (RFC §11.4 IDOR prevention); `ListMine` returns only the caller's own enrollments | This is where ADR-0012 is proven, not documented; `GetByID`/`ListMine` were previously untested |
| `internal/progress` | Enrollment transitions to `completed` only once every lesson in the *current* published version is done, not before; marking an already-complete lesson twice is a byte-for-byte no-op; a non-owner can't mark someone else's progress; `GetProgress` reflects real state (including after marking lessons complete) and rejects a non-owner | Proves the idempotency and version-currency rules in RFC §8.3; `GetProgress` was previously untested |
| `internal/platform/relay` | Bounded worker pool actually bounds concurrency, not just configures a number; idempotency holds across retries (fail twice, succeed once, exactly one `processed_events` row); a poison event stops retrying after `maxAttempts`; graceful shutdown drains an in-flight job's **database commit**, not just its Go function return | ADR-0021's worker pool proven, not documented — and the shutdown test caught a real bug during development (see the guide's own note below) |
| `internal/analytics` | `Repository` → `Service` → (what the handler calls) genuinely reflects a recompute, not just that each layer compiles independently; recompute reads only this module's own mirror tables (`user_role_mirror`, `course_mirror`, `enrollment_mirror`), never `course`/`identity` directly (ADR-0024); `user_role_mirror` ignores an out-of-order `identity.user_role_changed`/`user_registered` delivery; all 5 relay handlers (`handlePlatformCounts`, `handleCoursePublished`, `handleStudentEnrolled`, `handleStudentWithdrawn`, `handleCourseCompleted`) exercised through a real outbox event and a real relay, not a direct call to the underlying mirror/recompute function; `GetCourseStats`/`ListDailyEnrollments` reflect a real recompute/increment (DR-017 — these tables had no read path at all before) | First test this module had — the handler → service → repository layering itself was added in response to review (see `internal/analytics/README.md`); the ordering-guard test is a regression test for a bug caught live (a seeded instructor showing up as a student), not by inspection; the relay-handler tests close a real gap an audit found — the actual payload-decoding functions were never executed by any test before, only the repository functions they call; `GetCourseStats`/`ListDailyEnrollments` close a baseline-compliance gap — "computed" had been silently reported as "live" |
| `internal/platform/auth` | `RequireFreshPrivilege` (`middleware_integration_test.go`, real Redis): a cache miss defaults to token_version 1 (pass for a fresh token, reject anything else); a cached version matching the token's passes; a mismatch is rejected with `ErrTokenStale` specifically | ADR-0015's addendum — a named security fix — had zero test coverage until this |
| `internal/workflows` | `PublishCourseWorkflow`'s activities, wired to a REAL `course.Service` (real Postgres, real Redis — Temporal's own `testsuite.TestWorkflowEnvironment`, not a live Temporal server), actually promote the version, write a real `course_search_index` row, and write a real version-scoped Redis cache key reflecting the course's *post*-promotion state; a real `ValidateMetadata` failure (a draft with no modules) writes `publish_failed` with a clean, unwrapped error message to `course_versions` | Regression test for a real bug (ADR-0025): the cached payload built by `BuildOutline` (which runs before `PromoteAndPublish`) initially reflected the draft's pre-promotion shape — `draft_version_id` still set, state still `publishing` — so the first cache hit after any publish served a course that looked unpublished. The failure-path test proves the real `MarkPublishFailed` forwarding chain lands in Postgres, not just that it's *called* (the mocked-activity tests below only prove that) |

Run: `make test-integration`, or target one package: `go test -tags=integration -race -v ./internal/enrollment/...`.

### HTTP/API — a real `gin.Engine`, real `httptest` requests

Same build tag (`integration`) and same real Postgres/Redis as the tier above — the distinction is what layer gets exercised. Every test in the tier above calls `Service` methods directly in Go; none of them ever go through `handler.go`'s route registration, request binding, or auth middleware. An audit this session confirmed that gap was total — **zero tests anywhere sent a real HTTP request through a real `gin.Engine`** — and it's exactly what let a real bug through uncaught: two `GET` routes in `internal/course/handler.go` with conflicting wildcard names (`:slug` vs `:id`) that panicked gin's router at boot, found only by actually starting `course-api` (ADR-0025), not by any test.

Each of the five HTTP-serving modules (`internal/identity`, `internal/course`, `internal/enrollment`, `internal/progress`, `internal/analytics`) now has a `*_http_test.go` file that: boots the module's real `RegisterRoutes` against a real `gin.Engine` (this alone is the regression test for the router-panic bug class — a conflicting route registration panics at boot, which this test would hit immediately); sends a malformed request body to a bound endpoint and asserts `400`, not a 500 or a panic; calls a protected route with no `Authorization` header (`401`) and, where applicable, a valid token with the wrong role (`403`); and drives at least one full authenticated round trip over real HTTP (a real JWT built via `auth.IssueAccessToken`, a real request, a real response body) so routing, binding, middleware, the service layer, and response serialization are all proven to work together at least once, not just in isolation.

Scope is deliberate, not exhaustive: boot + binding + auth per module, not full success/every-error-status coverage of every one of the ~35 endpoints across these five modules — the service layer already covers most of that ground; this tier exists to catch what only running the real HTTP stack can catch.

Run: `go test -tags=integration -race ./internal/identity/... ./internal/course/... ./internal/enrollment/... ./internal/progress/... ./internal/analytics/...` (same command as the tier above — these live in the same packages, just different files).

### Concurrency — the highest-value tier (RFC §18.3)

Not a separate build tag — these live inside the `integration` tier because they need a real database to be meaningful. Singled out here because they catch a class of bug invisible to every other kind of test.

**`TestEnroll_SeatLimit_NeverExceededUnderConcurrency`** (`internal/enrollment/service_integration_test.go`) is the one to read first if you're new to this codebase. 30 real goroutines call `Enroll` simultaneously against a course with a 10-seat limit. The test asserts three things independently: exactly 10 calls succeed, exactly 20 return `course_full`, and — separately — the database's `enrollment_count` column and the actual count of `active` enrollment rows both equal 10. That third check exists because a bug could make the *count of successful Go function calls* look right while the *database* is still wrong (e.g. a counter that increments but a row that doesn't insert, or vice versa).

Without ADR-0012's row lock, this test doesn't reliably fail — it's *flaky*, which is worse: it passes most runs and fails under load, exactly mirroring how the bug it catches would show up in production (fine until a real launch-day spike).

**`TestEnroll_DuplicateAttempt_ExactlyOneSucceeds`** is the same shape applied to duplicate-enrollment prevention: 10 concurrent identical requests from one student, exactly one succeeds, enforced by the database's partial unique index rather than an application-level check that would itself race.

**`internal/platform/relay/relay_integration_test.go`** is the other one worth reading closely, specifically for `TestRelay_GracefulShutdown_DrainsInFlightWork`. Its first version asserted only that an in-memory flag was set after shutdown — and passed, against a real bug (the worker was handing in-flight jobs the already-cancelled shutdown context, so the handler's Go code finished but its database commit silently failed). The fixed version asserts on the database row instead. The lesson generalizes: a concurrency test that checks "did the goroutine run" is weaker than one that checks "did the goroutine's *effect* persist" — the gap between those two is exactly where this kind of bug hides.

**`TestLogin_PerAccountRateLimit_BlocksAfterThreshold`** (`internal/identity/service_integration_test.go`) rounds this out from the shared-state-synchronization side (RFC §7's "Rate limiter state" example): it burns the per-account GCRA budget with wrong-password attempts, then asserts the *correct* password is still rejected as rate-limited — proving the limiter blocks, not just that it's wired in.

### Workflow — Temporal's own test framework, mocked activities

§18.6's tier, unblocked now that the workflow exists (M2, ADR-0025). Lives in `internal/workflows/publish_workflow_test.go`, no build tag — fast, no Docker, no DB. `testsuite.WorkflowTestSuite` runs `PublishCourseWorkflow` for real; `env.OnActivity(...)` mocks each activity so these tests assert on *orchestration* alone (call order, concurrency, failure handling), independent of `internal/workflows/publish_workflow_integration_test.go`'s real-Postgres/Redis coverage of what each activity actually does.

| Test | What it checks | Why it matters |
|---|---|---|
| `TestPublishCourseWorkflow_HappyPath_RunsFullGraphInOrder` | Every activity in RFC §7.4's graph is called exactly once, in the right shape, and `MarkPublishFailed` is never called | Baseline: the graph wires together the way the diagram says it does |
| `TestPublishCourseWorkflow_ValidateMetadataFails_StopsBeforePromote` | A `ValidateMetadata` failure calls `MarkPublishFailed` and never reaches `PromoteAndPublish` | Proves RFC §7.4's "no compensation needed" design — nothing before promotion is undone because nothing before it was ever visible |
| `TestPublishCourseWorkflow_VerifyAssetsFails_StillWaitsOnComputeMetadata` | `ComputeMetadata` is still called (and its mock satisfied) even though its sibling `VerifyAssets` fails | Proves the two actually run concurrently, not sequentially with an early return — a workflow-logic version of the same question `internal/platform/relay`'s concurrency tests ask of the relay |

Run: `go test ./internal/workflows/...` (no tag needed).

### Contract and query-shape tiers — not yet implemented

Two tiers RFC §18 specifies that don't exist yet, tracked here rather than silently absent:

- **Contract tests** (§18.5) — event schema `BACKWARD`-compatibility checks against the Schema Registry. Blocked on Protobuf schemas existing, which is M3 scope (ADR-0008).
- **Query-shape tests** (§18.4) — mechanical assertions on query count per request, to catch N+1 regressions automatically rather than by code review. Worth adding once there's a second list endpoint to compare against; `internal/course`'s catalogue query is already written as a single raw-SQL join specifically to avoid needing this yet.
- **Security tests** as their own explicit tier (auth bypass, IDOR probing, mass-assignment attempts, injection against raw-SQL paths) — today, ownership and IDOR checks are exercised incidentally by the integration and HTTP-level tests above (e.g. `TestUpdateDraft_RejectsNonOwner`, `TestMarkComplete_RejectsNonOwner`, `TestGetByID_ReturnsOwnEnrollment_RejectsOthers`, the HTTP tier's 401/403 cases), not by a dedicated adversarial suite. A follow-up, not a gap papered over.

## Writing a new test

- **Unit test**: no database dependency, tests one function/method in isolation. Put it in the same package, `_test.go` suffix, no build tag.
- **Integration test**: needs Postgres (and/or Redis). Put it in the same package as `_integration_test.go` (or `service_integration_test.go`, matching this codebase's convention), with `//go:build integration` as the first line, and use `test/integration/testenv.Setup(t)` to get connected clients — never hand-roll container setup.
- **HTTP-level test**: a module adding or changing a route should extend its `*_http_test.go` (`//go:build integration`), not just rely on the service-layer tests — `gin.SetMode(gin.TestMode)`, a real `gin.New()` engine, the module's real `RegisterRoutes`, driven with `httptest.NewRecorder()`/`httptest.NewRequest()`. At minimum, a new route should be covered by the file's existing "boots without panicking" test picking it up automatically (it will, since that test just calls `RegisterRoutes`) — add a dedicated case only if the route has binding/auth behavior worth asserting on specifically.
- **Relay handler test**: a module adding a new outbox event consumer should test it the way `internal/enrollment/handlers_integration_test.go` does (the original correct example) — a real event written via `outbox.Write`, a real `relay.New(...)` with the handler registered, polled until the expected state appears — not a direct call to whatever repository function the handler happens to call, which skips the handler's own payload-decoding logic entirely.
- **Every test file gets a header comment stating what it checks and why that check matters** (RFC §18.8) — not just what it calls. If you can't articulate what failure the test would catch, that's a sign the test (or the code it covers) needs more thought before either is written.
