# Testing guide

Every test category SmartCourse uses, what it checks, why that check matters, and how to run it. This is the index RFC §18.8 requires: a future contributor deciding whether a change is safe should be able to answer "what would break" from this document, not by reading every test file.

## Quick reference

| Command | Runs | Needs Docker? |
|---|---|---|
| `make test` | Unit tests | No |
| `make test-race` | Unit tests, race detector on | No |
| `make test-integration` | Integration + concurrency + HTTP-level + workflow tests | Yes |
| `cd services/course && go test -tags=integration -race ./...` | One module (replace the directory with any module: `libs/auth`, `services/identity`, ...) | Yes |
| `make check-link-graph`, `make check-module-graph` | The build-graph and module-graph guards (`scripts/`): per-binary package budgets and forbidden imports, and "no service requires another service" | No |
| `make test-e2e` | The container tier: every binary as a process against real Postgres, Redis, Kafka, Schema Registry, MongoDB, Mailpit and Temporal (`test/README.md`) | Yes |
| `make verify-deliverables` | Live checks against a running stack (`scripts/verify-deliverables.sh`, rows of `docs/plans/week-3-acceptance-matrix.md`); rows for unbuilt features print PENDING and do not fail | A running stack |

**`go test ./...` at the repo root tests nothing.** The repo is 33 Go modules (ADR-0026, `go.work`: 24 under `libs/`, the six services, `tools/seed`, `tools/guardcheck` and `test/e2e`) and Go does not cross module boundaries. The `make` targets above run the command in every module with `GOWORK=off` (`scripts/for-each-module.sh`), so each module is tested exactly as it builds on its own.

CI (`.github/workflows/ci.yml`) runs the full set — build and `go vet` of every module with `GOWORK=off`, the link-graph and module-graph guards, `golangci-lint` per module (`depguard` covers the boundary inside `services/course`; boundaries between services are the Go module graph), migrations against a real Postgres service container, the pending-E2E guard (`make check-pending-e2e`), a separate `e2e` job for the container tier (`make test-e2e`), then `scripts/for-each-module.sh go test -race -tags=integration ./...` with `POSTGRES_DSN`/`REDIS_ADDR` set. The `-tags=integration` flag was missing until ADR-0025 (M2): every `//go:build integration` file — including the enrollment seat-limit concurrency test, the one RFC §18.3 calls "the highest-value tier" — was silently excluded from CI since the suite existed, found while verifying M2's own new integration tests actually ran. The job's declared Postgres/Redis service containers and its own migration step are themselves redundant now: every integration test provisions its own disposable containers via `testenv.Setup`, and nothing reads `POSTGRES_DSN`/`REDIS_ADDR` directly — left in place as a separate, lower-priority cleanup rather than touched here.

## Test tiers

### Unit — no database, no network

Domain logic tested against pure functions and in-memory state. Fast, run constantly during development.

| Package | What it checks |
|---|---|
| `libs/auth` | argon2id hash/verify round-trips and rejects wrong passwords; the dummy hash (timing-safety, RFC §11.3) is itself valid; JWT issue/parse round-trips; expired tokens rejected; wrong signing key rejected; **`alg:none` / alg-confusion rejected** (`TestParseAccessToken_RejectsAlgNone` — this is the specific check that closes a real vulnerability class, not a generic parser test); `middleware_test.go` (new): `RequireAuth` rejects a missing/malformed header and an invalid token, and on success populates the request context with the caller's identity; `RequireRole` rejects when no identity is present and when the role isn't in the allowed set — both via a real `httptest`+`gin.Engine`, this repo's first use of that pattern, not a bare function call |
| `libs/config` | `Load()`'s fail-fast validation: every required env var missing individually and in combination (confirming errors *aggregate*, not just that the first one reported); `JWT_SIGNING_KEY`'s minimum-length check; a malformed optional var (bad int/bool/duration) is rejected rather than silently falling back to its default |
| `libs/httpx` | `EncodeCursor`/`DecodeCursor` round-trip exactly (including sub-second time precision); a malformed cursor (bad base64, or valid base64 that isn't valid JSON) is rejected as a client error, not a panic; `ClampLimit`'s boundary behavior (zero/negative, over-max, in-range) |

Run: `make test`, or one library: `cd libs/auth && go test ./...`.

### Integration — real Postgres (and Redis, where relevant), via `testcontainers-go`

RFC §18.2's rule: **mocks are not used for the database.** A mock proves the code called the method it was written to call; it cannot prove a constraint holds, a transaction rolls back correctly, or a partial index behaves as designed. Every test in this tier spins up a real, disposable Postgres (and Redis) container via `libs/testenv`, creates the per-service roles with the real `scripts/db-roles.sh`, applies every migration set in order (`platform identity course analytics notification cutover`, schema-per-service, ADR-0024), and tears it down after — no shared state between tests, no fixtures to go stale. A service's tests connect as that service's own role (`env.ServiceDB(t, "course")`: role `svc_course`, search path `course,public`), exactly as the binary does, so a test that reaches another schema or an unqualified table of another service fails with `permission denied`; `env.DB` is the owner connection (search path `public`) for DDL and cross-schema fixtures, so unqualified use fails loudly.

Build tag: `integration`. Excluded from `go test ./...` by default so unit tests stay fast; included by `make test-integration`.

### HTTP/API — a real `gin.Engine`, real `httptest` requests

Same build tag (`integration`) and same real Postgres/Redis as the tier above — the distinction is what layer gets exercised. Every test in the tier above calls `Service` methods directly in Go; none of them ever go through `handler.go`'s route registration, request binding, or auth middleware. An audit this session confirmed that gap was total — **zero tests anywhere sent a real HTTP request through a real `gin.Engine`** — and it's exactly what let a real bug through uncaught: two `GET` routes in `services/course/course/handler.go` with conflicting wildcard names (`:slug` vs `:id`) that panicked gin's router at boot, found only by actually starting `course-api` (ADR-0025), not by any test.

Each of the five HTTP-serving modules (`services/identity/identity`, `services/course/course`, `services/course/enrollment`, `services/course/progress`, `services/analytics/analytics`) now has a `*_http_test.go` file that: boots the module's real `RegisterRoutes` against a real `gin.Engine` (this alone is the regression test for the router-panic bug class — a conflicting route registration panics at boot, which this test would hit immediately); sends a malformed request body to a bound endpoint and asserts `400`, not a 500 or a panic; calls a protected route with no `Authorization` header (`401`) and, where applicable, a valid token with the wrong role (`403`); and drives at least one full authenticated round trip over real HTTP (a real JWT built via `auth.IssueAccessToken`, a real request, a real response body) so routing, binding, middleware, the service layer, and response serialization are all proven to work together at least once, not just in isolation.

Scope is deliberate, not exhaustive: boot + binding + auth per module, not full success/every-error-status coverage of every one of the ~35 endpoints across these five modules — the service layer already covers most of that ground; this tier exists to catch what only running the real HTTP stack can catch.

Run: `make test-integration` (same command as the tier above — these live in the same packages, just different files), or one service: `cd services/identity && go test -tags=integration -race ./...`.

### Concurrency — the highest-value tier (RFC §18.3)

Not a separate build tag — these live inside the `integration` tier because they need a real database to be meaningful. Singled out here because they catch a class of bug invisible to every other kind of test.

**`TestEnroll_SeatLimit_NeverExceededUnderConcurrency`** (`services/course/enrollment/service_integration_test.go`) is the one to read first if you're new to this codebase. 30 real goroutines call `Enroll` simultaneously against a course with a 10-seat limit. The test asserts three things independently: exactly 10 calls succeed, exactly 20 return `course_full`, and — separately — the database's `enrollment_count` column and the actual count of `active` enrollment rows both equal 10. That third check exists because a bug could make the *count of successful Go function calls* look right while the *database* is still wrong (e.g. a counter that increments but a row that doesn't insert, or vice versa).

Without ADR-0012's row lock, this test doesn't reliably fail — it's *flaky*, which is worse: it passes most runs and fails under load, exactly mirroring how the bug it catches would show up in production (fine until a real launch-day spike).

**`TestEnroll_DuplicateAttempt_ExactlyOneSucceeds`** is the same shape applied to duplicate-enrollment prevention: 10 concurrent identical requests from one student, exactly one succeeds, enforced by the database's partial unique index rather than an application-level check that would itself race.

**`libs/relay/relay_integration_test.go`** is the other one worth reading closely, specifically for `TestRelay_GracefulShutdown_DrainsInFlightWork`. Its first version asserted only that an in-memory flag was set after shutdown — and passed, against a real bug (the worker was handing in-flight jobs the already-cancelled shutdown context, so the handler's Go code finished but its database commit silently failed). The fixed version asserts on the database row instead. The lesson generalizes: a concurrency test that checks "did the goroutine run" is weaker than one that checks "did the goroutine's *effect* persist" — the gap between those two is exactly where this kind of bug hides.

**`TestLogin_PerAccountRateLimit_BlocksAfterThreshold`** (`services/identity/identity/service_integration_test.go`) rounds this out from the shared-state-synchronization side (RFC §7's "Rate limiter state" example): it burns the per-account GCRA budget with wrong-password attempts, then asserts the *correct* password is still rejected as rate-limited — proving the limiter blocks, not just that it's wired in.

### Workflow — Temporal's own test framework, activities registered by name

§18.6's tier (M2, ADR-0025; the workflow moved to its own service, ADR-0035). Lives in `services/publishing/publish/workflow_test.go` and `replay_test.go`, no build tag — fast, no Docker, no DB (the publishing service has none). `testsuite.WorkflowTestSuite` runs `PublishCourseWorkflow` for real; mocked activities are registered under the contract names from `libs/contracts/publishing`, so these tests assert on *orchestration* alone (call order, concurrency, failure handling, the activity queue), independent of `services/course/activities`' real-Postgres/Redis coverage of what each activity does.

| Test | What it checks | Why it matters |
|---|---|---|
| `TestPublishCourseWorkflow_HappyPath_RunsFullGraphInOrder` | Every activity in RFC §7.4's graph is called exactly once, in the right shape, and `MarkPublishFailed` is never called | Baseline: the graph wires together the way the diagram says it does |
| `TestPublishCourseWorkflow_ValidateMetadataFails_StopsBeforePromote` | A `ValidateMetadata` failure calls `MarkPublishFailed` and never reaches `PromoteAndPublish` | Proves RFC §7.4's "no compensation needed" design — nothing before promotion is undone because nothing before it was ever visible |
| `TestPublishCourseWorkflow_VerifyAssetsFails_StillWaitsOnComputeMetadata` | `ComputeMetadata` is still called (and its mock satisfied) even though its sibling `VerifyAssets` fails | Proves the two actually run concurrently, not sequentially with an early return — a workflow-logic version of the same question `libs/relay`'s concurrency tests ask of the relay |

Further tests in the same files pin the wire format (ADR-0035): the set of activities the workflow schedules equals `publishing.ActivityNames()` (`TestPublishCourseWorkflow_ScheduledActivitiesEqualTheContract`), every activity goes to the activity queue including on the failure path, the failure reason is bounded and never raw error text (`TestSafeReason`), and history replay (`TestReplay_*`) fails on a renamed activity. `services/publishing/independence_test.go` fails if the module requires or imports any other service. The combined workflow-plus-activities path over a real Temporal server is proven only by the container E2E scenarios (E01 runs a publish end to end; E12, the failure path, is still a pending stub).

Run: `cd services/publishing && go test ./...` (no tag needed).

### Adversarial tests — written to break the system (module-split phase 5)

Added after the module split by two separate review sessions with a deliberate "assume the code and the ADRs are wrong until a test proves otherwise" brief: 42 new test files and 4 fuzz targets (159 new top-level tests: 113 in the default suite and 46 bug reproducers). They are named `*adversarial*`, `*security*` and `*bugrepro*`. What they found, how each defect was fixed, and what is still imperfect is in `docs/plans/module-split-findings.md`; what held up is listed there too.

**Build tags.**

- `//go:build integration` — runs in the default suite (`make test-integration`) and must stay green and deterministic. Each file was run with `-race -count=3` before being committed.
- `//go:build integration && bugrepro` — reserved for a **reproducer of a known, unfixed defect**: a test that fails today by design and is excluded from the default suite so CI stays meaningful. **There are none at the moment**: all 46 reproducers written in this phase were fixed, lost the tag, and are now ordinary regression tests with their original names (`TestBug_*`, `TestBugrepro_*`). Use the tag again for the next bug you find before you fix it: write the failing test behind `bugrepro`, fix the code, then drop the tag in the same change. Run tagged tests with `go test -tags='integration bugrepro' -run TestBug ./...` in the module.

### Contract and query-shape tiers — not yet implemented

Two tiers RFC §18 specifies that don't exist yet, tracked here rather than silently absent:

- **Contract tests** (§18.5) — event schema `BACKWARD`-compatibility checks against the Schema Registry. Blocked on Protobuf schemas existing, which is M3 scope (ADR-0008).
- **Query-shape tests** (§18.4) — mechanical assertions on query count per request, to catch N+1 regressions automatically rather than by code review. Worth adding once there's a second list endpoint to compare against; `services/course/course`'s catalogue query is already written as a single raw-SQL join specifically to avoid needing this yet.
- **Security tests** as their own explicit tier (auth bypass, IDOR probing, mass-assignment attempts, injection against raw-SQL paths) — today, ownership and IDOR checks are exercised incidentally by the integration and HTTP-level tests above (e.g. `TestUpdateDraft_RejectsNonOwner`, `TestMarkComplete_RejectsNonOwner`, `TestGetByID_ReturnsOwnEnrollment_RejectsOthers`, the HTTP tier's 401/403 cases), not by a dedicated adversarial suite. A follow-up, not a gap papered over.

## Writing a new test

- **Unit test**: no database dependency, tests one function/method in isolation. Put it in the same package, `_test.go` suffix, no build tag.
- **Integration test**: needs Postgres (and/or Redis). Put it in the same package as `_integration_test.go` (or `service_integration_test.go`, matching this codebase's convention), with `//go:build integration` as the first line, and use `libs/testenv.Setup(t)` to get connected clients — never hand-roll container setup.
- **HTTP-level test**: a module adding or changing a route should extend its `*_http_test.go` (`//go:build integration`), not just rely on the service-layer tests — `gin.SetMode(gin.TestMode)`, a real `gin.New()` engine, the module's real `RegisterRoutes`, driven with `httptest.NewRecorder()`/`httptest.NewRequest()`. At minimum, a new route should be covered by the file's existing "boots without panicking" test picking it up automatically (it will, since that test just calls `RegisterRoutes`) — add a dedicated case only if the route has binding/auth behavior worth asserting on specifically.
- **Event consumer test**: a service adding a new event consumer should test it through the consumer's own path, not a direct call to whatever repository function the handler happens to call (which skips the handler's own payload-decoding logic). Either deliver a decoded event with `relay.Deliver` (the handler and its `processed_events` marker in one transaction, as `services/analytics/analytics/handlers_integration_test.go` does), or write a real event with `outbox.Write` and run a real `relay.New(...)` with the handler registered, as `services/course/enrollment/handlers_integration_test.go` does. Run the test as the service's own role (`env.ServiceDB`).
- **Wiring test for a new binary**: give it a `config_test.go` (loads with only its declared variables), a unit wiring test (components, topics, queues) and an integration test that runs the real `wire` through `runtime.Run`; add it to `scripts/check-link-graph.sh` and the E2E harness.
- **Every test file gets a header comment stating what it checks and why that check matters** (RFC §18.8) — not just what it calls. If you can't articulate what failure the test would catch, that's a sign the test (or the code it covers) needs more thought before either is written.
