# services/analytics/analytics

Platform and course-level aggregate metrics (RFC §4.3, §9; SmartCourse.md FR-5). The handlers here run in `analytics-worker` as Kafka consumers (consumer `analytics-aggregator`, through `libs/eventbus`; ADR-0033). They are written against the `libs/relay` handler contract (`relay.Handler`, `relay.Deliver`); ADR-0021 records how the module started as the relay's first consumer.

## Why this module looks the way it does

**`service.go` is thin, but it exists, and that was a real fix, not a formality.** Unlike `identity`/`course`/`enrollment`/`progress`, this module's main work doesn't react to direct HTTP writes — it reacts to outbox events, via handler functions run by the worker's consumers (`handlers.go`). The only synchronous surface is reads (`/analytics/*`). Until review caught it, that one read went `Handler` → `*gorm.DB` directly, skipping the service layer every other module has — an easy shortcut to take when a module "only" has one endpoint, and exactly the kind of inconsistency that's invisible until someone copies the pattern elsewhere. `Service.GetPlatformSnapshot` just delegates to `Repository`, but the layering is what's load-bearing: a future second read endpoint has an obvious place to put real logic, instead of a second ad-hoc `*gorm.DB` call.

**This module owns its own Postgres schema (`analytics`) and never queries `course.courses`, `course.enrollments`, or `identity.users` directly (ADR-0024).** That wasn't true before ADR-0024 — `RecomputePlatformSnapshot`/`RecomputeCourseStats` used to read those tables straight, in the same database but across what are now schema boundaries. Three mirror tables replace that: `user_role_mirror`, `course_mirror`, `enrollment_mirror` (`repository.go`'s `Upsert*`/`Insert*`/`UpdateEnrollmentMirrorStatus` functions), upserted row-by-row as `handlers.go` consumes each relay event. They hold exactly the fields this module's Recompute* functions need — not a general-purpose copy of another service's tables.

**Every aggregate is still recomputed from source, not incrementally maintained** — only what counts as "source" moved. `RecomputePlatformSnapshot` and `RecomputeCourseStats` (`repository.go`) run a fresh `COUNT`/`AVG` against this module's own mirror tables on every relevant event, rather than a running `+1`/`-1` against another service's live tables. This is still ADR-0017's rebuildability principle, applied eagerly instead of on ADR-0017's 60-second schedule (the scheduled `Reconciler` now exists: see Reconciliation below; scheduling it is the worker's job): a bug in a counter is still fixable by recomputing, it just recomputes from here now. It trades a slightly heavier query per event for the complete absence of an entire bug class: an incremental counter that drifts from reality because of a bug, a missed event, or a manual correction has no way to self-correct; a recompute-from-source is correct by construction every time it runs.

**`user_role_mirror.last_event_id` exists because recompute-from-mirror reopened a race recompute-from-live-table never had.** Nothing guarantees order between handlers — Kafka orders only within a partition, the consumer runs several handlers concurrently, and events from different services are not ordered at all — so a user's `identity.user_registered` and a later `identity.user_role_changed` can have their handlers finish in either order. Before ADR-0024, that didn't matter: a recompute always read whatever `identity.users.role` currently was, regardless of event processing order. A naive mirror upsert (`role = EXCLUDED.role`, unconditionally) reintroduces the race — whichever event's handler finishes last wins, which can silently revert a promotion back to `student`. This was caught live, not in a test, while verifying ADR-0024 end to end: a seeded instructor showed up as a student in `GET /analytics/platform`. `UpsertUserRoleMirror` only applies an update when the incoming event's outbox id (the `id` of the row in the producing service's own outbox, `identity.outbox`, a monotonic `BIGSERIAL`, carried in the Kafka `outbox_id` header as `relay.DecodedEvent.OutboxID`; 0 for a record without the header, which the guard treats as older than anything applied) is newer than what's already recorded — see `mirror_integration_test.go`'s `TestUpsertUserRoleMirror_IgnoresOutOfOrderDelivery` for the regression test. `course_mirror` and `enrollment_mirror` don't need the same guard: `course_mirror` only ever sets `published = true` (idempotent regardless of order),. `enrollment_mirror` now has the same `last_event_id` guard (migration 000002, F-09): a withdrawal that overtakes its enrollment creates the row (enrolled_at NULL) and is kept when student_enrolled lands.

**`daily_enrollments` is the one aggregate the event path increments rather than recomputes** — "an enrollment happened on this UTC day" is an immutable historical fact once true, so the simpler operation is also correct on that path. See the comment on `IncrementDailyEnrollment`. The scheduled `Reconciler` (below) still re-derives the buckets from `enrollment_mirror`, so a bump that was lost or doubled is repaired like any other counter.

**`progress.course_completed`'s payload doesn't carry `course_id`** — only `enrollment_id`, `student_id`, and (since ADR-0024) `completed_at`. `handleCourseCompleted` resolves `course_id` via `CourseIDForEnrollment`, a lookup against this module's own `enrollment_mirror` (populated at enroll time) — never a query into `course.enrollments` (ADR-0024). The event stays deliberately minimal at the source (RFC); a consumer that needs more joins against its own data.

## What this closes, and what it doesn't

FR-5 names nine metrics (SmartCourse.md; DR-021). **9 of 9 have a source** (DR-026): the ninth, Failed Events / Workflow Issues, is served in two halves, and its failed-events half needs MongoDB.

| # | Metric | Where it is served | Backed by |
|---|---|---|---|
| 1-3 | Total students, total instructors, total courses published | `GET /analytics/platform` | `platform_snapshot` |
| 4 | Average courses per student | `GET /analytics/platform` | `platform_snapshot` |
| 5 | Course completion rate | `GET /analytics/courses/{id}` | `course_stats` |
| 6 | Average time to complete | `GET /analytics/courses/{id}` | `course_stats.avg_completion_s` |
| 7 | New enrollments over time | `GET /analytics/courses/{id}/daily-enrollments` | `daily_enrollments` |
| 8 | **Most popular courses** (new, Week 3) | `GET /analytics/popular-courses` | Redis sorted set `analytics:popular_courses`, reconciled from `course_stats` + `course_mirror` every `Reconciler.Run`; Postgres fallback |
| 9 | Failed events / workflow issues | `GET /analytics/issues` (admin only) | Failed events from MongoDB `failed_events` (`services/analytics/failedevents`, attached in `cmd/analytics-api/wire.go`); workflow issues from `workflow_issue_stats`, fed by `course.publish_failed` (`workflow_issues.go`). 503 while MongoDB is unset or unreachable |

(Metrics 1-4 are four numbers on one route, so the count of nine is by metric, as the baseline lists them.)

**Most Popular Courses** ranks published courses by enrollments (active plus completed, the same definition as `course_stats.total_enrollments`), ties broken by course id, courses with no enrollments omitted, default 10 and at most 50 entries. Any authenticated user may read it, like the platform totals: it exposes course ids and counts only. The read goes to Redis first (`ZREVRANGE`, 300 ms budget); if Redis is absent, down, slow or empty it falls back to the identical ranking in Postgres, and a Redis problem is logged, never returned. The sorted set carries a 5-minute TTL, so if the reconciler stops, readers drift to Postgres instead of serving a stale rank forever. Freshness is therefore up to one reconciler interval (RFC §9.1's 60 s) when Redis answers. The response has no course title: `course_mirror` does not store one.

**Failed Events / Workflow Issues** needs the dead-letter store (MongoDB `failed_events`) and workflow failure counts. This package links neither: `issues.go` defines the two narrow interfaces and `Service.WithIssueSources` attaches them. `GET /analytics/issues` is admin-only (401/403) and runs `auth.RequireFreshPrivilegeStrict` after the role check: the token's version must match the cached one in Redis, and a cache miss (for example after a Redis flush) is 401 `token_stale`, not "version 1", because analytics cannot read identity's tables to check (ADR-0024). Redis unreachable, or no Redis client wired, is 503. An admin is refused here after a flush until identity's re-seeder rewrites the key (versions above 1, one 15 s tick) or the admin logs in, refreshes or calls an identity `/me` or admin route (version 1). See the `libs/auth` README.

- **Failed events: live.** `services/analytics/failedevents` implements `FailedEventsSource` over `libs/mongostore` (one aggregation over `failed_events`, no payloads) and `cmd/analytics-api/wire.go` attaches it. analytics-api is therefore the one HTTP service allowed to link `libs/mongostore` (the link-graph rule was relaxed for it alone; ADR-0031 deviation note). The report has `total`, `unresolved` (parked), `replayed`, `by_event_type` and `by_consumer` (parked only) and `oldest_unresolved_age_seconds` (null when nothing is parked). MongoDB connects lazily on first use, retried at most every 5 s, so startup and every other route are independent of it: with `MONGO_URI` unset or MongoDB unreachable the route answers 503 (`ErrSourceUnavailable`), never zeros.
- **Workflow issues: live (DR-026).** Failure facts live in the course schema, which this module may not read (ADR-0024), so `course.publish_failed` (emitted by `services/course/course` when a version ends in `publish_failed`, from the workflow's failure step or the stale-publish reconciler) is mirrored here: migration `000004` adds `publish_failures` (one row per event, keyed by event id) and `workflow_issue_stats` (the count). `handlePublishFailed` inserts the row and recomputes the count under a row lock, so concurrent failures are all counted and a redelivery counts once; `Reconciler.Run` recomputes every count from the mirror. `NewWorkflowIssuesSource(db)` reads `workflow_issue_stats` and `cmd/analytics-api/wire.go` attaches it whether or not MongoDB is configured. `GET /analytics/issues` therefore always returns `workflow_issues` as an object: `{"failed": N, "by_workflow": {"PublishCourseWorkflow": N}}`.
  - **What it counts:** publish attempts that ended in `publish_failed` since the event existed: a cumulative count of failures, not of versions currently failing (a version that failed twice counts twice; one that later published still counts). Publishing is the only workflow, so `by_workflow` has one key.
  - **Not backfilled:** failures before the event existed are not counted (the only record is `course_versions.publish_error`, in the course schema). The metric starts at zero at deploy.
  - **Without a workflow source** (`WithIssueSources(failed, nil)`, only in tests now) the service still reports the section as `null` rather than a made-up zero.

### Instructor ownership (deviation from DR-022's "instructors may read any course")

`course.course_published` now carries `instructor_id`; `handleCoursePublished` stores it in `course_mirror.instructor_id` (migration `000003`, nullable). Per-course routes now allow: admins any course; an instructor only a course whose recorded owner they are; a student only a course they are actively or completed-enrolled in. Everything else is 404, like the other ownership denials (F-36), and identical to the response for an unknown course.

The honest limits: `course_mirror` rows written before the migration have no owner and this schema cannot read `course.courses` to find one (ADR-0024), so there is no backfill. Such a row is **readable by admins only** until the next `course_published` for that course fills it (publishing again emits the event). The reconciler cannot fill it: it recomputes from mirrors and the mirror has nothing to recompute an owner from. A course analytics has never seen published is a 404 for instructors (before this change they got zeros), while admins still get the neutral zeros. An event without `instructor_id` (or the nil UUID) never erases a recorded owner. If existing deployments need the owners sooner, the lead can have services/course re-emit `course_published` or supply a one-off backfill; nothing here does that.

## Reconciliation (RFC §9.2, ADR-0017)

`NewReconciler(db, rdb).Run(ctx)` (`reconcile.go`) recomputes `platform_snapshot`, every course's `course_stats` row and its `daily_enrollments` buckets from the mirror tables, then rebuilds the Redis sorted set (built under a temporary key and swapped in with `RENAME` in one `MULTI`; an empty ranking deletes the key). It is idempotent. It does not schedule itself: whatever hosts the periodic jobs calls `Run` about every 60 seconds. A nil `rdb` skips the sorted set; a Redis failure is returned as an error after Postgres has already been repaired.

*Against the handlers:* handlers and `Run` follow one discipline. Every recompute first takes the aggregate's row lock (`course_stats` row, then `platform_snapshot` row, always in that order) and reads the mirror in a later statement, so under READ COMMITTED a writer that waited for the lock reads what the other committed and cannot overwrite a newer total with a stale one (this also tightens two handlers racing on the same course). `Run` does one short transaction per course and one for the platform, so it never holds two course locks and cannot form a lock cycle. The `last_event_id` guards on the mirrors are untouched. `TestReconciler_WaitsForInFlightHandlerAndDoesNotOverwriteItsResult` pins this deterministically; `TestReconciler_ConcurrentWithHandlersAndSecondRun` exercises it under `-race`.

*Against a second `Run`:* a transaction-scoped `pg_advisory_xact_lock` makes the second wait for the first, then repeat the same idempotent work.

*Daily buckets:* rebuilt from every mirror row with a known `enrolled_at`, regardless of status (the event path counts an enrollment on its day even if the student later withdrew). A withdrawn-before-enrolled placeholder row has no `enrolled_at` yet and is not counted until `student_enrolled` lands, matching the event path.

What reconciliation cannot do: the mirrors themselves are only as right as the events that fed them. It repairs drift between mirrors and aggregates, not a missing event (that is replay's job).

## Testing

`service_integration_test.go` (build tag `integration`, real Postgres): `TestGetPlatformSnapshot_ReflectsRecompute` seeds `user_role_mirror` directly, runs `RecomputePlatformSnapshot` inside a transaction exactly as the relay's handler does, and asserts the HTTP-facing `Service.GetPlatformSnapshot` reads back what was just written — proving the `Repository` → `Service` → handler path genuinely works end to end, not just that each piece compiles.

`mirror_integration_test.go`: `TestRecomputeCourseStats_ReflectsEnrollmentMirror` drives the same mirror-write-then-recompute sequence `handlers.go` drives for a full enroll/withdraw/complete scenario. `TestUpsertUserRoleMirror_IgnoresOutOfOrderDelivery` is the regression test for the `last_event_id` ordering guard described above.

**`handlers_integration_test.go` drives every handler through the consumer's own path.** Each handler (`handlePlatformCounts`, `handleCoursePublished`, `handleStudentEnrolled`, `handleStudentWithdrawn`, `handleCourseCompleted`, `handlePublishFailed`) is run through `relay.Deliver` (the handler and the `analytics.processed_events` marker in one transaction, as the analytics-worker's Kafka consumers do), with the JSON payload shape the producing services publish written out as a literal (analytics may not import those services). Analytics has no outbox, so nothing is written to one. That proves each handler's own `json.Unmarshal` against the real payload shape, which a direct repository call never exercises. All tests that touch Postgres connect as `svc_analytics` (`env.ServiceDB(t, "analytics")`, search path `analytics,public`); DDL-class fixtures (TRUNCATE, the migration down/up tests) use the owner connection with qualified names.

**`analytics_http_test.go` is this module's first HTTP-level test** (RFC §18.2, this repo's new tier): boots `RegisterRoutes` against a real `gin.Engine` (the regression test for a router-registration panic class found live elsewhere in this project — invisible to every `Service`-level test, only catchable by actually starting a server), confirms `GET /analytics/platform` enforces `RequireAuth` (any authenticated caller may read platform totals; per-course routes are enrollment/role gated, 404 on denial), and drives one real HTTP request against a seeded snapshot row end to end through routing, middleware, and JSON serialization. `TestGetCourseStats_RealRequest_ReflectsSeededRow` does the same for `GET /analytics/courses/{id}`.

`TestGetCourseStats_ReflectsRecompute` and `TestListDailyEnrollments_ReturnsTimeSeries` (`service_integration_test.go`) are the regression tests for the "computed but unreadable" gap itself: both start from a course with no row (asserting the same zeros-not-an-error behavior `GetPlatformSnapshot` already established), then seed `enrollment_mirror` rows / call `IncrementDailyEnrollment` directly, run the real `Recompute*` function, and confirm the new `Service` methods read back exactly what was written.

**Week 3 tests.** `reconcile_integration_test.go` (drift healed by hand-corrupting every aggregate, idempotence, rebuild from truncated aggregates, sorted-set refresh and TTL, empty-ranking clear, Redis down, concurrent Run versus handlers and a second Run, the deterministic lock-then-read check); `popular_integration_test.go` (ranking moves when handlers change the data and the reconciler runs; Redis-first; Redis empty, down and absent fall back to Postgres; unpublished and empty courses excluded; HTTP 401/200/400 matrix); `instructor_ownership_integration_test.go` (owner 200, non-owner 404 indistinguishable from unknown course, admin 200, student gated, owner-less row admin-only until republished, owner never erased, migration `000003` down then up); `issues_http_test.go` (admin-only, 401/403/503/500 matrix and the response shape, against fakes). The pre-existing tests that granted any instructor access to any course were changed to the new rule.
