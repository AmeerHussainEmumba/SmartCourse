# internal/analytics

Platform and course-level aggregate metrics (RFC §4.3, §9; SmartCourse.md FR-5). The first real consumer registered with `internal/platform/relay` — see that package's README and `docs/adr/smartcourse-adr.md` ADR-0021 for why this module exists now rather than waiting for Kafka in M3.

## Why this module looks the way it does

**`service.go` is thin, but it exists, and that was a real fix, not a formality.** Unlike `identity`/`course`/`enrollment`/`progress`, this module's main work doesn't react to direct HTTP writes — it reacts to outbox events, via handler functions registered with the relay (`handlers.go`). The only synchronous surface is a read: `GET /analytics/platform`. Until review caught it, that one read went `Handler` → `*gorm.DB` directly, skipping the service layer every other module has — an easy shortcut to take when a module "only" has one endpoint, and exactly the kind of inconsistency that's invisible until someone copies the pattern elsewhere. `Service.GetPlatformSnapshot` just delegates to `Repository`, but the layering is what's load-bearing: a future second read endpoint has an obvious place to put real logic, instead of a second ad-hoc `*gorm.DB` call.

**This module owns its own Postgres schema (`analytics`) and never queries `course.courses`, `course.enrollments`, or `identity.users` directly (ADR-0024).** That wasn't true before ADR-0024 — `RecomputePlatformSnapshot`/`RecomputeCourseStats` used to read those tables straight, in the same database but across what are now schema boundaries. Three mirror tables replace that: `user_role_mirror`, `course_mirror`, `enrollment_mirror` (`repository.go`'s `Upsert*`/`Insert*`/`UpdateEnrollmentMirrorStatus` functions), upserted row-by-row as `handlers.go` consumes each relay event. They hold exactly the fields this module's Recompute* functions need — not a general-purpose copy of another service's tables.

**Every aggregate is still recomputed from source, not incrementally maintained** — only what counts as "source" moved. `RecomputePlatformSnapshot` and `RecomputeCourseStats` (`repository.go`) run a fresh `COUNT`/`AVG` against this module's own mirror tables on every relevant event, rather than a running `+1`/`-1` against another service's live tables. This is still ADR-0017's rebuildability principle, applied eagerly instead of on ADR-0017's 60-second schedule (that scheduled reconciliation path doesn't exist yet — see below): a bug in a counter is still fixable by recomputing, it just recomputes from here now. It trades a slightly heavier query per event for the complete absence of an entire bug class: an incremental counter that drifts from reality because of a bug, a missed event, or a manual correction has no way to self-correct; a recompute-from-source is correct by construction every time it runs.

**`user_role_mirror.last_event_id` exists because recompute-from-mirror reopened a race recompute-from-live-table never had.** The relay's worker pool (default 4 workers, `internal/platform/relay`) has no per-aggregate ordering — a user's `identity.user_registered` and a later `identity.user_role_changed` can have their handlers finish in either order. Before ADR-0024, that didn't matter: a recompute always read whatever `identity.users.role` currently was, regardless of event processing order. A naive mirror upsert (`role = EXCLUDED.role`, unconditionally) reintroduces the race — whichever event's handler finishes last wins, which can silently revert a promotion back to `student`. This was caught live, not in a test, while verifying ADR-0024 end to end: a seeded instructor showed up as a student in `GET /analytics/platform`. `UpsertUserRoleMirror` only applies an update when the incoming event's outbox id (`platform.outbox`'s own monotonic `BIGSERIAL`) is newer than what's already recorded — see `mirror_integration_test.go`'s `TestUpsertUserRoleMirror_IgnoresOutOfOrderDelivery` for the regression test. `course_mirror` and `enrollment_mirror` don't need the same guard: `course_mirror` only ever sets `published = true` (idempotent regardless of order), and `enrollment_mirror`'s status transitions are mutually exclusive per enrollment (an enrollment can't be both withdrawn and completed, so there's only ever one "second event" per row, and `InsertEnrollmentMirror`'s own upsert deliberately excludes `status` from what it overwrites).

**`analytics_daily_enrollments` (now `daily_enrollments`) is the one genuine exception** to recompute-from-source — it's incremented, not recomputed, because "an enrollment happened on this UTC day" is an immutable historical fact once true. There's no drift risk a recompute would guard against, so the simpler operation is also the correct one. See the comment on `IncrementDailyEnrollment`.

**`progress.course_completed`'s payload doesn't carry `course_id`** — only `enrollment_id`, `student_id`, and (since ADR-0024) `completed_at`. `handleCourseCompleted` resolves `course_id` via `CourseIDForEnrollment`, a lookup against this module's own `enrollment_mirror` (populated at enroll time) — never a query into `course.enrollments` (ADR-0024). The event stays deliberately minimal at the source (RFC); a consumer that needs more joins against its own data.

## What this closes, and what it doesn't

Closes 7 of 10 metrics from SmartCourse.md FR-5: total students, total instructors, total courses published, average courses per student (`GET /analytics/platform`, backed by `platform_snapshot`); course completion rate and average time to complete (`GET /analytics/courses/{id}`, backed by `course_stats`); new enrollments over time (`GET /analytics/courses/{id}/daily-enrollments`, backed by `daily_enrollments`). `course_stats`/`daily_enrollments` were written by the relay's handlers since ADR-0024 but had no read path at all until a baseline-compliance audit found the gap — "computed" isn't the same as "live," and the earlier version of this README conflated the two. Still missing: "Most Popular Courses" (needs a ranking read, not yet built), and "Failed Events / Workflow Issues" (needs the MongoDB `failed_events` collection, M3 scope — the relay's own give-up path currently only logs, per ADR-0021's documented limitation).

**Scheduled reconciliation (ADR-0017's other half) doesn't exist yet.** Today's numbers are event-driven only. They should already be correct given the recompute-from-mirror approach above, but there's no periodic job independently re-deriving them as a check — that's a real, honest gap, not a subtle one.

## Testing

`service_integration_test.go` (build tag `integration`, real Postgres): `TestGetPlatformSnapshot_ReflectsRecompute` seeds `user_role_mirror` directly, runs `RecomputePlatformSnapshot` inside a transaction exactly as the relay's handler does, and asserts the HTTP-facing `Service.GetPlatformSnapshot` reads back what was just written — proving the `Repository` → `Service` → handler path genuinely works end to end, not just that each piece compiles.

`mirror_integration_test.go`: `TestRecomputeCourseStats_ReflectsEnrollmentMirror` drives the same mirror-write-then-recompute sequence `handlers.go` drives for a full enroll/withdraw/complete scenario. `TestUpsertUserRoleMirror_IgnoresOutOfOrderDelivery` is the regression test for the `last_event_id` ordering guard described above.

**`handlers_integration_test.go` closes the gap the previous version of this README flagged as a natural next addition.** All 5 relay handlers (`handlePlatformCounts`, `handleCoursePublished`, `handleStudentEnrolled`, `handleStudentWithdrawn`, `handleCourseCompleted`) are now driven through the real `outbox` → `relay` → handler path — a real event row written via `outbox.Write`, a real `relay.Relay` polling and dispatching it — not a direct call into the `repository.go` functions they wrap. That distinction matters: every test above this one proves the SQL is right; these prove each handler's own `json.Unmarshal` against the real payload shape `internal/identity`/`internal/course`/`internal/enrollment`/`internal/progress` actually write is correct, which a direct repository call can never catch (a renamed JSON field, a wrong type assertion) since it never goes through decoding at all.

**`analytics_http_test.go` is this module's first HTTP-level test** (RFC §18.2, this repo's new tier): boots `RegisterRoutes` against a real `gin.Engine` (the regression test for a router-registration panic class found live elsewhere in this project — invisible to every `Service`-level test, only catchable by actually starting a server), confirms `GET /analytics/platform` enforces `RequireAuth` (and only that — no role restriction; any authenticated caller can read platform-wide totals), and drives one real HTTP request against a seeded snapshot row end to end through routing, middleware, and JSON serialization. `TestGetCourseStats_RealRequest_ReflectsSeededRow` does the same for `GET /analytics/courses/{id}`.

`TestGetCourseStats_ReflectsRecompute` and `TestListDailyEnrollments_ReturnsTimeSeries` (`service_integration_test.go`) are the regression tests for the "computed but unreadable" gap itself: both start from a course with no row (asserting the same zeros-not-an-error behavior `GetPlatformSnapshot` already established), then seed `enrollment_mirror` rows / call `IncrementDailyEnrollment` directly, run the real `Recompute*` function, and confirm the new `Service` methods read back exactly what was written.
